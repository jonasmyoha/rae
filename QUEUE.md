- [ ] #664 Add generic total (non-optional) `List(T)` read accessors: `copyAtDefault(index:)` and `copyAtFallback(index:, fallback:)`. Motivation: after #642 every optional ends in `if let`, so reading one element of a same-length parallel array (a common structure-of-arrays pattern) becomes verbose, and a downstream app grew ad-hoc per-type helpers (`floatListValue`, `intListValue`, …) that are all one generic function. INVESTIGATED (verified today on bin/rae, no compiler change): BOTH shapes already work as ordinary generic library functions —
  (a) CALLER-PROVIDED fallback → `copyAtFallback`: `func copyAtFallback(T: type, this: view List(T), index: view Int, fallback: own T) ret T { if let value: T = this.copyAt(index: index) { ret value } ret fallback }` — verified returning the real value for Float/Int and a struct fallback for `List(Point)`; returns `T`, never an optional.
  (b) SYNTHESIZED default (no fallback arg) → `copyAtDefault`: `func copyAtDefault(T: type, this: view List(T), index: view Int) ret T { if let value: T = this.copyAt(index: index) { ret value } var fallback: T  ret fallback }` — a bare `var fallback: T` triggers the existing recursive auto-init (`emit_auto_init`, c_backend.c:879) which zero-inits ANY type: primitives→0, String→empty, List→empty, nested struct→recurse. Verified even for a heap-owning struct (`Bag { name: String  items: List(Int) }`): the default is an empty String + empty List, returned and dropped with `RAE_MEM_STATS outstanding=0` (no leak, no double-free). So the "how does List(T) build a fallback for EVERY struct" question has a clean answer — it doesn't construct anything special; `var x: T` auto-init already handles every type generically.
  NAMES (DECIDED by the downstream owner): `copyAtDefault` (auto-init zero) + `copyAtFallback` (caller value). Both keep the `copyAt` stem so they group under the copy/view/mod trichotomy (autocomplete-discoverable) and both read as a matched pair; "Or" was dropped from the earlier `copyAtOr`/`copyAtOrDefault` sketch because it only carried readability, not meaning. `copyAtDefault(index: i)` is the everyday `[]`-replacement (used broadly downstream); `copyAtFallback(index: i, fallback: x)` when the caller has a meaningful non-zero fallback.
  Scope: add both to lib/core.rae beside `copyAt`/`viewAt`/`modAt`; doc both; tests for Float, Int, a plain struct, and a heap-owning struct (both the explicit-fallback and the auto-init default). On #642 alignment: neither conflicts — #642 forbids the SILENT auto-unwrap (`let x: T = list.copyAt(...)` inventing a value behind the reader's back); these are EXPLICIT, named accessors the programmer chooses to call, so the default is chosen by name, not compiler-invented behind their back. Note default/fallback only make sense for `copy` (there is no sensible "default view"/"fallback mod"), so the `copyAt` prefix is the right and only trichotomy slot for them. Not a language feature: both are plain generic stdlib functions (form (b) leans on the existing `emit_auto_init` via a bare `var fallback: T`), so this is a small lib addition, not a compiler change. Deps: none (built on #642's `if let`).
  CONVERGENCE (owner's preferred end state): once Rae has optional parameters / overloading (wanted, not yet supported), `copyAtDefault` becomes the single unified form — `copyAtDefault(index:, opt fallback: T)` where an OMITTED fallback uses the auto-init default and a PROVIDED one overrides (the "default" IS the fallback in that case). `copyAtFallback` then folds into `copyAtDefault` (kept as a deprecated alias or removed). So implement both names now, but treat `copyAtDefault` as the primary/keeper and `copyAtFallback` as the interim explicit-fallback overload; when optional params land, refile the merge. NOTE: the downstream app already uses `copyAtDefault` broadly (defined locally as a stopgap; deletes its local def and resolves to this stdlib one when it lands).
